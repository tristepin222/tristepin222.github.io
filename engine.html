Why I built this

I started this project to understand the low-level architecture beneath modern game engines, rather than simply scripting on top of existing commercial platforms. Building a game engine from scratch forced me to address core hardware interactions and strict memory boundaries directly.

By writing my own renderer, custom memory pools, scene management, and tooling interface, I gained a deep appreciation for the trade-offs involved in real-time systems design. It serves as a playground to study performance limits, Data-Oriented Design (DOD), cache locality, and graphics API pipelines.

Working at this level requires strong fundamentals in C++ memory management, systems design, and direct GPU programming, shifting the focus from using tools to building them.

What it is

The prototype is a fully functioning, two-project visual development workspace that splits engine runtime systems from client sandbox logic:

  • Real-time 3D rendering
    The engine renders 3D objects in real time using the Vulkan graphics API, the same low-level graphics technology used in professional game productions. Geometry is processed on the GPU each frame using custom-written shader programs.
  • Built-in visual editor
    The engine includes an interactive editor panel, similar to Unity's Inspector, to browse scene objects, rename them, and adjust their position, color, and shape in real time without restarting the application.
  • 3D transform gizmos
    Clicking an object in the 3D viewport shows a set of interactive handles, the same colored arrows and rings found in Unity or Blender. These handles can be dragged to move, rotate, or resize objects directly inside the scene.
  • Click-to-select in the viewport
    Clicking anywhere in the 3D viewport selects the object under the cursor. This is done with raycasting: a ray is projected from the camera through the mouse position into the 3D scene to find which object was clicked.
  • Scene save & load
    The full scene, including every object, its position, color, and type, can be saved to a file and reloaded later. The system is extensible by design: custom object types added by a game developer are automatically included in saves, with no changes needed to the engine itself.
  • Component-based object model
    Objects are built by attaching small, focused data pieces called components: a position, a mesh, a material, a camera. This is the same pattern used by Unity and Unreal. It keeps the codebase flexible and makes adding new behavior straightforward.
  • Modular engine / game split
    The engine is compiled as a separate static library that a game project links against, similar to how Unity separates its runtime from a user project. The included sandbox game shows how small a game-side script can be when the engine handles the infrastructure.
  • Multi-threaded job system
    Distributes complex workload operations (like skeletal animations and physics updates) across CPU cores using a task-parallel job scheduler supporting dynamic index-chunk loop partitioning and lock-free yielding synchronization.
  • GPU skeletal skinning & IK
    Deforms vertices dynamically on the GPU using Linear Blend Skinning (LBS). Orientation paths are smoothly interpolated using spherical linear interpolation (SLERP), coordinated by Forward Kinematics, and adjusted dynamically using 2-bone and multi-joint FABRIK Inverse Kinematics (IK) solvers.
  • 3D rigid body physics & SAT
    Simulates physical dynamics with linear and angular integration, drag coefficients, and bounciness. Resolves multi-shape collisions (Sphere, AABB, OBB) using Separating Axis Theorem (SAT) projections and applies 3D rotational impulses to handle realistic bounces, tilts, and friction.
  • Direct FBX asset loader
    Integrates the ufbx library to natively import FBX Binary and ASCII assets at runtime. Automatically unrolls vertex index mappings, deduplicates vertex attributes, and bakes complex multi-curve animation data at 30 FPS into a compact runtime buffer.

Key challenges

Vulkan is an extremely explicit graphics API. Unlike higher-level libraries, it offers zero safety fallback at runtime: if a pipeline barrier, swapchain transition, or descriptor binding contains a single misalignment, the GPU fails silently with a blank screen. Overcoming this involved writing robust debug logging integrations using Vulkan validation layers and structuring diagnostic render passes to isolate pipeline states.

Another significant obstacle was handling real-time viewport raycasting. Clicking an entity in the viewport requires transforming 2D screen coordinates back through the inverse camera projection and view matrices, projecting a 3D ray into the scene, and evaluating bounding volume intersections. Resolving this required robust linear algebra structures and caching bounding shapes to maintain editor performance.

A major multi-threading challenge emerged during parallel loop scheduling in the Job System. Early versions used stack-allocated condition variables on the main thread to coordinate worker threads. If the main thread finished waiting early, the stack frame was deallocated, causing worker threads to trigger memory access violations when trying to signal the destroyed primitive. I resolved this use-after-free bug by replacing stack-allocated synchronization with a lock-free, atomic counter (`std::atomic`) combined with cooperative spin-yielding (`std::this_thread::yield()`).

Handling FBX animations presented challenges due to split vertex attributes (e.g. UVs and normals mapped per-index) and complex, layered Bezier keyframe curve math. I solved this by unrolling index layouts using a deduplicating vertex hash map and baking animation curves into linear transform samples at a constant 30 FPS rate.

Lastly, OBB collision resolution required implementing the Separating Axis Theorem (SAT) across 15 candidate projection axes, identifying the minimum penetration axis, and resolving rotational responses by transforming inverse inertia tensors to world space to apply equal-and-opposite angular impulses at the contact point.

How it works

The project is structured around a modular static library model. The engine compiles into a standalone C++ library, which the sandbox game links against. This isolates the core engine runtime (rendering pipelines, GLFW window, input processing) from the game-specific logic. This runtime-sandbox isolation creates a clean, frictionless iteration cycle for developers. The visual editor embeds Dear ImGui directly via Vulkan descriptors, drawing the rendered scene viewport into ImGui panels to provide an integrated workspace for content creators.

At the core is a custom Entity Component System (ECS) implementing Data-Oriented Design (DOD). Instead of using heavy, pointer-chasing object inheritance hierarchies, game entities are lightweight identifiers, and their data is stored in contiguous, type-specific memory blocks (component pools). This data-oriented design optimizes CPU cache utilization by ensuring that tight loop passes during physics, rendering, and skeletal updates achieve near-perfect L1/L2 cache locality, preventing CPU pipeline stalls due to cache misses.

The visual editor relies on Dear ImGui, binding Vulkan texture descriptors to draw the rendered viewport directly inside ImGui window panels. Entity selection updates the inspector view dynamically, allowing real-time modification of component data structures serialized to JSON formatting.

The Job System manages a thread pool containing $N-1$ workers. To minimize heap manager overhead during the runtime frame loop, the system avoids dynamic allocations. Tasks are pushed to the thread-safe queue as lightweight lambdas capturing bounds by reference, fitting entirely within the small buffer optimization (SBO) of std::function. When heavy loops are processed (like skeletal skinning and collision updates), the main thread partitions the iteration space into chunks, enqueuing them without triggering the system heap. Workers execute these chunks, distributing joint and physics calculations across CPU cores.

Skeletal meshes deformation is calculated in the GPU vertex shader. Bone indices and weights are carried by the vertex buffer (`ivec4` and `vec4`), while joint offset matrices are bound as a descriptor uniform palette supporting up to 256 bones.

The Physics Engine operates in updates: it integrates gravity forces to update velocities and positions, detects intersections using narrow-phase geometric checkers, estimates contact normals/points, and resolves collisions using a 3D impulse solver.
