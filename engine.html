Why I built this

I started this project to understand the low-level architecture beneath modern game engines, rather than simply scripting on top of existing commercial platforms. Building a game engine from scratch forced me to address core hardware interactions and strict memory boundaries directly.

By writing my own renderer, custom memory pools, scene management, and tooling interface, I gained a deep appreciation for the trade-offs involved in real-time systems design. It serves as a playground to study performance limits, Data-Oriented Design (DOD), cache locality, and graphics API pipelines.

Working at this level requires strong fundamentals in C++ memory management, systems design, and direct GPU programming, shifting the focus from using tools to building them.

What it is

The prototype is a fully functioning, two-project visual development workspace that splits engine runtime systems from client sandbox logic:

  • Real-time 3D rendering
    The engine renders 3D objects in real time using the Vulkan graphics API, the same low-level graphics technology used in professional game productions. Geometry is processed on the GPU each frame using custom-written shader programs.
  • Built-in visual editor
    The engine includes an interactive editor panel, similar to Unity's Inspector, to browse scene objects, rename them, and adjust their position, color, and shape in real time without restarting the application.
  • 3D transform gizmos
    Clicking an object in the 3D viewport shows a set of interactive handles, the same colored arrows and rings found in Unity or Blender. These handles can be dragged to move, rotate, or resize objects directly inside the scene.
  • Click-to-select in the viewport
    Clicking anywhere in the 3D viewport selects the object under the cursor. This is done with raycasting: a ray is projected from the camera through the mouse position into the 3D scene to find which object was clicked.
  • Scene save & load
    The full scene, including every object, its position, color, and type, can be saved to a file and reloaded later. The system is extensible by design: custom object types added by a game developer are automatically included in saves, with no changes needed to the engine itself.
  • Component-based object model
    Objects are built by attaching small, focused data pieces called components: a position, a mesh, a material, a camera. This is the same pattern used by Unity and Unreal. It keeps the codebase flexible and makes adding new behavior straightforward.
  • Modular engine / game split
    The engine is compiled as a separate static library that a game project links against, similar to how Unity separates its runtime from a user project. The included sandbox game shows how small a game-side script can be when the engine handles the infrastructure.
  • Multi-threaded job system
    Distributes complex workload operations (like skeletal animations and physics updates) across CPU cores using a task-parallel job scheduler supporting dynamic index-chunk loop partitioning and lock-free yielding synchronization.
  • GPU skeletal skinning & blend spaces
    Deforms vertices dynamically on the GPU using Linear Blend Skinning (LBS). Features spherical linear interpolation (SLERP), hierarchical Forward Kinematics, 1D & 2D Freeform Cartesian blend space trees, direct WASD keyboard controller input binding, and 2-bone / FABRIK Inverse Kinematics (IK) solvers.
  • 3D rigid body physics & SAT
    Simulates physical dynamics with linear and angular integration, drag coefficients, and bounciness. Resolves multi-shape collisions (Sphere, AABB, OBB) using Separating Axis Theorem (SAT) projections and applies 3D rotational impulses to handle realistic bounces, tilts, and friction.
  • Direct FBX asset loader
    Integrates the ufbx library to natively import FBX Binary and ASCII assets at runtime. Automatically unrolls vertex index mappings, deduplicates vertex attributes, and bakes complex multi-curve animation data at 30 FPS into a compact runtime buffer.
  • Static reflection engine
    Features a custom pre-processor and code generator (reflection_generator) that parses C++ annotations to generate component field layouts. This eliminates manual bindings, powering automatic JSON scene serialization and editor UI inspector panels.
  • Interactive sandbox showcase game
    Includes a compiled sandbox game demonstrating 3D rigid body dynamics, SAT bounding collisions, and character movement driven by custom state machine controllers with a physics-based gravity gun script.
// challenges

Key challenges

Vulkan Verbosity & Safety: Vulkan has zero runtime safety fallback. Overcoming silent black screens involved implementing validation layer diagnostics and structured render passes to isolate pipeline states.

Racy Stack Allocations in Job System: Worker synchronization originally used stack-allocated primitives, leading to use-after-free corruption when the main thread exited early. This was resolved with a lock-free atomic chunk counter and cooperative spin-yielding (std::this_thread::yield()).

FBX Importing & Curve Baking: Parsing split vertex attributes and Bezier keyframes was slow. This was solved by unrolling indices via a deduplicating vertex hash map and pre-baking animations into 30 FPS local transform arrays.

OBB Collision & Rotational Impulses: Resolving oriented bounding box intersections required implementing Separating Axis Theorem (SAT) across 15 axes and transforming local inertia tensors to world space for realistic 3D torque/impulse response.

// architecture

How it works

Engine / Sandbox Isolation: The core runtime compiles as a separate static library, completely decoupling core infrastructure from client game logic. A Dear ImGui visual editor binds to Vulkan texture descriptors to render the viewport directly into editor panels.

Data-Oriented ECS: Components are stored contiguously in memory pools using the Swap-Remove pattern. By avoiding deep pointer-chasing inheritance, systems achieve optimal L1/L2 cache line locality.

Task-Parallel Job System: Loop operations (skinning, physics) are partitioned into chunks and pushed to a lock-free thread pool queue, avoiding heap allocations via reference-capturing lambda SBO.

GPU Skinning & Physics: Skinned meshes deform in the vertex shader using a shared UBO joint palette. The narrow-phase physics engine integrates gravity, detects Sphere/AABB/OBB intersections, and applies rotational impulses.
