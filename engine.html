Personal Project · 2024–2025

C++ Vulkan Game Engine

// overview

What is this project?

This is a custom game engine built entirely from scratch, with no off-the-shelf engine underneath it. The goal was to understand exactly how game engines like Unity or Unreal work on the inside — by building one myself.

It handles everything a real engine does: rendering 3D objects on screen, letting you edit a scene visually, saving and loading that scene to a file, and giving you a clean, scriptable way to define game behavior.

Why build an engine instead of just making a game? Because understanding the foundation is what separates a developer who uses tools from one who can build them. This project is proof that I can work at that lower level.

// what it does

Key features

  • Real-time 3D rendering
    The engine renders 3D objects in real time using the Vulkan graphics API — the same low-level technology used in AAA games. Every frame, geometry is sent to the GPU and drawn with custom-written shaders.
  • Built-in visual editor
    A fully interactive editor panel (similar to Unity's Inspector or Unreal's Details panel) lets you browse all objects in the scene, rename them, tweak their position, color, and shape, all in real time without restarting the engine.
  • 3D transform gizmos
    Click on any object in the 3D viewport and a set of interactive handles appears — the same colored arrows and rings you'd find in Unity or Blender. Drag them to move, rotate, or resize objects directly in the scene.
  • Click-to-select in the viewport
    You can click directly on a 3D object in the viewport to select it. This uses a mathematical technique called raycasting that translates the 2D position of your mouse into a ray shot through the 3D world to detect which object you're pointing at.
  • Scene save & load
    The entire scene — every object, its position, color, and type — can be saved to a file and reloaded later. The serialization system is fully extensible: custom objects added by a game developer are automatically included in saves without touching the engine code.
  • Component-based object model
    Every object in the world is built by combining small, focused pieces of data called components — a position, a shape, a color, a camera. This is the same design pattern used by Unity and Unreal, and it keeps the codebase clean and easy to extend.
  • Modular engine / game split
    The engine is packaged as a separate static library that a game project links against — just like how Unity the engine is separate from your Unity project. The included sandbox game demonstrates how thin and clean a "game script" can be when the engine does the heavy lifting.
// challenges & learnings

What was hard — and what I learned

Building a rendering engine means working without a safety net. There is no error message that says "your triangle is in the wrong place" — the screen just stays black. Debugging requires reading GPU validation logs, understanding memory alignment rules, and reasoning about what happens on hardware you can't directly observe.

The biggest architectural challenge was designing systems that don't depend on each other. For example, the scene serializer originally had to "know about" every type of object that could exist. I redesigned it into a plugin-style registry where new object types register themselves — meaning the engine stays clean regardless of what a game developer adds.

This project taught me to think in terms of interfaces and contracts rather than just "code that works." Every system boundary is a design decision, and making the wrong one costs hours of refactoring later.
